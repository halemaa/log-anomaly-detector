# log-anomaly-detector

A small tool that reads a web server log and flags windows of time when
the error rate spikes. Written in pure Python, no dependencies.

Useful for: SOC analysts reviewing nginx/Apache logs, on-call engineers
spot-checking an incident timeline, anyone who wants a simple "when did
things go wrong today?" tool.

Demonstrates the **sliding window** algorithm on a real problem — one
pass over the log, O(n) time.

## See it work

The repo ships with `generate_sample_log.py`, which writes a realistic
one-hour log containing two planted "incidents" — moments when the error
rate deliberately spikes.

```bash
python generate_sample_log.py   # writes sample.log (~20k lines)
python detect.py sample.log
```

Output:

```

Window: 60s  ·  Threshold: 10.0%  ·  Min sample: 10

Found 9 anomalies:
------------------------------------------------------------------------------
  2026-11-10 09:15:16  error rate  10.2%  (36 of 353 in last 60s)
  2026-11-10 09:16:16  error rate  35.5%  (122 of 344 in last 60s)
  2026-11-10 09:17:16  error rate  32.1%  (109 of 340 in last 60s)
  2026-11-10 09:18:16  error rate  34.3%  (110 of 321 in last 60s)
  2026-11-10 09:19:16  error rate  31.6%  (102 of 323 in last 60s)
  2026-11-10 09:20:16  error rate  24.5%  (76 of 310 in last 60s)
  2026-11-10 09:45:28  error rate  10.1%  (36 of 355 in last 60s)
  2026-11-10 09:46:28  error rate  24.9%  (77 of 309 in last 60s)
  2026-11-10 09:47:28  error rate  14.6%  (44 of 302 in last 60s)
```

The detector caught both planted incidents (09:15–09:20 and 09:45–09:47)
and didn't false-alarm on the normal ~1% baseline noise. The cooldown
keeps it from flooding the output with one line per second during a
single sustained spike.

## Run against a real log

```bash
python detect.py /var/log/nginx/access.log
python detect.py access.log --window 30 --threshold 0.05
python detect.py access.log --window 300 --threshold 0.02 --min-sample 50
```

Flags:

- `--window`     window size in seconds (default 60)
- `--threshold`  error rate above which to flag (default 0.10)
- `--min-sample` minimum requests in a window before flagging (default 10)

Exit code is non-zero when anomalies are found, so this fits cleanly
into a cron job or an alerting pipeline.

## The algorithm, in one paragraph

Walk through the log once. Keep a `deque` of the entries in the current
window — the last `N` seconds. For every new entry: append it to the
right side of the deque, then drop everything from the left side that's
older than the window. Count errors in the deque. Compare the rate to a
threshold. Because each entry is added once and removed once, the whole
scan is O(n) over the log, with memory bounded by the window size.

See [`theory/`](theory/) for the longer explanation of why sliding window
works, what the complexity analysis actually looks like, and how this
same pattern shows up in rate limiters, intrusion detection, and
trading systems.

## Extending

- **Per-path anomalies** — track error rates per endpoint, not just overall.
  A spike confined to `/api/payments` is more actionable than an overall
  spike.
- **Baseline-relative threshold** — compare the current window to a
  long-term baseline (last hour, last day) instead of a fixed rate.
- **Multiple severity tiers** — warn at 5%, alert at 10%, page at 30%.
- **Output JSON or SARIF** — pipe into a real alerting system.
- **Watch mode** — tail a file and alert in real time instead of scanning
  historical logs.
